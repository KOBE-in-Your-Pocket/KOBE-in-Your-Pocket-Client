# App Store リリース計画（2026年9月中旬リリース目標）

作成日: 2026-07-02（同日改訂: バックエンドの進捗とチームベロシティ実績を反映）
対象: 本リポジトリ（KOBE in Your Poket Client / Expo SDK 56 + React Native 0.85）
目的: App Store 審査で指摘されうるリスクの洗い出し、現行アーキテクチャの改善点、9月中旬リリースに向けたスプリント計画をまとめる。

> **前提事実（改訂で追加）**: バックエンド（`KOBE-in-Your-Poket-Client-Backend` / Kotlin + Spring Boot + PostgreSQL）は基本的な雛形が完成しており、**2〜3日でデプロイまで持っていける状態**。tourism コンテキストはスポット登録・一覧（多言語）まで実装済み。したがって本計画では**バックエンド遅延をリスクとして扱わない**。

> 本ドキュメントは 2026-07-02 時点の `develop` ブランチのコードを実際に読んだ上での評価です。推測ではなくコード上の事実（ファイルパス付き）を根拠にしています。

## 1. App Store 審査で突っ込まれそうな点

優先度は「🔴 リジェクト直結」「🟡 指摘される可能性が高い」「🟢 提出前に整えれば良い」の3段階。

### 🔴 R-1. UGC（レビュー投稿）にモデレーション機構がない — Guideline 1.2

- **現状**: `src/features/tourism/ui/components/review-form.tsx` でレビュー投稿・編集・削除ができる。一方で **通報（report）・ユーザーブロック・不適切コンテンツのフィルタ・利用規約への同意** が一切ない。
- **Apple の要求（Guideline 1.2 – User-Generated Content）**: UGC を持つアプリは以下を全て備える必要がある。
  1. 不適切コンテンツのフィルタリング機構
  2. 通報（フラグ）機能
  3. 悪質ユーザーのブロック機能
  4. 連絡先の公開（開発者への問い合わせ手段）
- **改善案（v1 では投稿機能を出さないのが現実的）**:
  - **案A（推奨）**: v1 は**レビュー閲覧のみ**とし、投稿 UI をフィーチャーフラグで無効化する。バックエンド・認証・モデレーションが揃う v1.1 以降で投稿を解禁する。9月リリースを守るならこれ一択。
  - **案B**: 投稿を残すなら、通報ボタン + ブロック + NG ワードフィルタ + 利用規約同意 + 24時間以内に対応できる運用体制を8月中に作る。バックエンド未接続（後述 R-2）の現状では非現実的。

### 🔴 R-2. モック/プレースホルダーデータのまま提出するとリジェクト — Guideline 2.1 / 2.3.1

- **現状**:
  - 観光スポットは `src/features/tourism/infrastructure/api/mock-spots.ts` のハードコード7件。画像は Unsplash の直リンク。
  - レビューは `src/features/tourism/infrastructure/api/mock-reviews.ts` のシード + `use-review-store.ts`（メモリ保持、再起動で消える）。
  - ユーザーは `src/features/user/application/use-current-user.ts` の固定ユーザー「荒川蓮」+ `i.pravatar.cc` のダミーアバター。
  - 評価（★レーティング）は対応済みの良い状態: 捏造の固定値は削除済みで、`Spot.rating` が無いスポットは★を表示しない（`spot.ts` の optional 化）。今後は**独自評価フォーマット（自前レビュー集計）を実装する方針**で、v1.1 の投稿解禁とセットで表示開始する。
- **リスク**: 「デモ/未完成に見えるアプリ」「実在しない評価の表示」は 2.1（App Completeness）で確実に止まる。投稿したレビューが再起動で消えるのはバグ扱いされる。
- **改善案**:
  - スポットデータは**バックエンド API（tourism コンテキストは実装済み・2〜3日でデプロイ可能）経由の実データ**に差し替える。これが主軸。画像は**権利処理済みのもの**を S3 配信（`EXPO_PUBLIC_S3_IMAGE_BASE_URL` の仕組みは既にある）。
  - モックの★評価は v1 では**表示しない**か、「参考値」であることが分かる実データに差し替える。存在しない評価を見せるのが一番危ない。
  - 固定ユーザー・pravatar は投稿機能の無効化（R-1 案A）とセットで露出をなくす。

### 🔴 R-3. デバッグ画面が本番バンドルに含まれる — Guideline 2.3.1（隠し機能）

- **現状**: `src/app/debug/`（index / map / use-current-location）が Expo Router のルートとしてそのまま含まれ、`__DEV__` ガードが無い（grep で確認済み）。
- **リスク**: 審査員がディープリンク（`kobeinyourpoketclient://debug`）等で到達可能。「非公開の機能・デバッグメニュー」は 2.3.1 で指摘対象。
- **改善案**: `src/app/debug/_layout.tsx` で `if (!__DEV__) return <Redirect href="/" />;` を入れる（最小コスト）。理想は Metro の条件付き除外だが、9月目標ならガードで十分。

### 🟡 R-4. 権限の目的文字列が日本語のみ — 外国人観光客向けアプリとして致命的な矛盾

- **現状**: `app.config.ts` の `expo-location` プラグイン設定で `locationWhenInUsePermission` が日本語のみ。アプリ本体は ja/en/zh の3言語対応（`src/shared/lib/i18n/locales/`）。
- **リスク**: 審査自体は英語環境で行われる。英語端末で日本語の権限ダイアログが出ると、5.1.1（目的の明確な説明）で指摘されうる。プロダクトの主張（外国人観光客向け）とも矛盾する。
- **改善案**: `locales` 設定（`expo-localization` の `config` プラグインまたは `ios.infoPlist` + InfoPlist.strings）で en/zh/ja の3言語分の purpose string を用意する。

### 🟡 R-5. 避難所という安全情報の正確性・出典・免責 — Guideline 1.1 / 5.1.5

- **現状**: 避難所データは `mock-shelters.ts` を SQLite にシードする構成。出典表示・更新日時・免責事項が UI にない。
- **リスク**: 災害・安全系の情報は「不正確な情報がユーザーに実害を与えうる」として審査で厳しく見られる。また実際の利用者保護の観点でも必須。
- **改善案**:
  - データ出典を神戸市オープンデータ等の公的ソースに固定し、**出典・データ基準日を詳細画面とアプリ内クレジットに明記**。
  - 「最新の避難情報は自治体の発表を優先してください」等の免責文言を避難タブに追加。
  - オフラインで参照できる現行の SQLite 構成は防災アプリとして強み。審査ノートでもアピールポイントになる。

### 🟡 R-6. プライバシー関連の提出物一式が未整備

- **現状**: リポジトリにプライバシーポリシーへの言及なし。設定画面（`settings-screen.tsx`）は言語切替のみで、ポリシー・ライセンス・問い合わせ導線がない。
- **必要なもの**:
  1. **プライバシーポリシー URL**（App Store Connect 必須項目）。収集項目は位置情報（端末内利用のみ）+ ORS への経路リクエスト（座標が外部送信される点は明記が必要）。
  2. **App Privacy（Nutrition Labels）** の申告: 位置情報「アプリ機能のため / トラッキングなし」。トラッキングをしないので ATT は不要。
  3. **輸出コンプライアンス**: `ios.infoPlist` に `ITSAppUsesNonExemptEncryption: false` を入れて毎回の質問を回避。
  4. アプリ内の設定画面にプライバシーポリシー・OSS ライセンス・問い合わせ先のリンクを置く（1.2 の「連絡手段」要件も兼ねる）。
- **補足**: 現状アカウント作成が無いので「アカウント削除機能（5.1.1(v)）」は不要。**認証を後付けする場合は必須になる**ため、v1 で認証を入れない判断（R-1 案A）はここでも効いてくる。

### 🟡 R-7. 審査環境で動くか — 位置情報前提の機能のフォールバック

- **現状**: 現在地→スポットの徒歩経路（OpenRouteService）、距離順ソートなど、現在地が神戸近辺である前提の機能が多い。`dev-default-coordinates.ts` に開発用フォールバックはあるが本番挙動は要確認。
- **リスク**: 審査員はカリフォルニアから起動する。位置情報拒否時・遠隔地での起動時に空画面やエラーになると 2.1 で止まる。
- **改善案**:
  - 位置情報が無い/遠隔地でも「神戸中心の地図 + スポット一覧」が完全に機能することを実機で確認（`kobe-initial-region.ts` があるので土台はある）。
  - App Review 用の**審査ノート**に「神戸市向け観光アプリであり、遠隔地では現在地機能が距離表示のみ制限される」旨と操作手順を書く。

### 🟢 R-8. アプリ名・メタデータ

- `app.config.ts` の `name: 'KOBE-in-Your-Poket-Client'`。**「Poket」は「Pocket」のスペルミス**であり、`-Client` はホーム画面に出す名前として不適切。表示名（`ios.infoPlist.CFBundleDisplayName` / `name`)を製品名（例: `KOBE in Your Pocket`）に変更する。Bundle ID (`com.kobeinyourpocket.client`) は正しい綴りなのでそのままで良い。
- スクリーンショット（6.7"/6.1"）、説明文（en/ja/zh）、キーワード、サポート URL が必要。8月中に準備。

### 🟢 R-9. その他の技術的指摘候補

- **ORS API キーがクライアント埋め込み**（`EXPO_PUBLIC_OPENROUTESERVICE_API_KEY`、`use-route.ts:9`）: 審査でのリジェクト理由にはならないが、無料枠 2000 req/日をキー抜き取りで枯らされると**本番で経路機能が死ぬ**。v1 はレート制限リスクを許容するか、バックエンドプロキシ経由に変更（バックエンドのスコープ次第）。
- **OSM/ORS の帰属表示**: ORS の経路データは OpenStreetMap 由来。「© openrouteservice / © OpenStreetMap contributors」のクレジットをアプリ内（マップ画面 or クレジット画面）に表示するのがライセンス（ODbL）上必要。
- **`react-query-devtools` が dependencies に入っている**: devDependencies へ移動（バンドルには乗らないはずだが整理する）。
- **eas.json に production プロファイルが無い**: 現状 development 系のみ。`production`（`distribution: "store"`、`autoIncrement`）と `submit` プロファイルの追加が必要。

## 2. アーキテクチャ評価と改善点

### 2.1 良い点（維持すべき設計）

`docs/directory-structure.md` の「Modular Monolith × Feature-scoped Clean Architecture」は方針として妥当で、特に以下は評価できる。

- **evacuation モジュールは4層が機能している**: `domain/evacuation-shelter-repository.ts`（interface）→ `infrastructure/db/sqlite-evacuation-shelter-repository.ts`(実装) の依存性逆転が実際に守られており、SQLite シード + マイグレーション（drizzle）でオフラインファーストになっている。防災機能として正しい設計。
- ユースケース単位のユニットテストが層ごとに揃っている（`__tests__` が domain/application/infrastructure/ui 各層に存在）。
- i18n（ja/en/zh）・テーマ・位置情報が shared に分離されており、feature → shared の一方向依存が保たれている。

### 2.2 改善点

#### A-1. tourism モジュールが Repository パターンを迂回している（最重要）

- **現状**: evacuation は repository interface 経由だが、tourism は `application/use-spots.ts` 等の hooks が `infrastructure/api/mock-spots.ts` を直接参照している。つまり「モック→実 API」の差し替え点がモジュール内に分散している。
- **なぜ問題か**: 9月までに必ず「モック → 実データ」の差し替えが発生する（R-2）。差し替え口が interface に集約されていないと、この作業が UI まで波及する。
- **改善案**: evacuation と同じ形に揃える。
  1. `domain/spot-repository.ts`（`SpotRepository` interface）を定義
  2. `infrastructure/api/mock-spot-repository.ts`（現行モックのラップ）と、実データ用実装（S3 静的 JSON or バックエンド API）を用意
  3. application hooks は repository を注入して呼ぶ
  - こうしておけば「実 API が9月に間に合わない場合、静的 JSON バンドル + S3 画像で出す」というフォールバックが差し替え1点で済む。

#### A-2. データソース戦略の明文化

- バックエンド（tourism 実装済み、2〜3日でデプロイ可能）があるため、**観光スポットの実データ化はバックエンド API 接続が主軸**。クライアント側の作業は「A-1 の Repository interface 化 → API 実装への差し替え」に集約される。
  - **観光スポット**: バックエンド `GET /spots` 系 API に接続。あわせて evacuation と同様に SQLite キャッシュ（オフライン対応）を挟むと、審査時のネットワーク不安定にも強くなる。
  - **レビュー**: R-1 案Aどおり v1 は閲覧のみ（もしくは機能ごと非表示）。バックエンドの Review 集約は実装済みなので、**モデレーション（通報・ブロック）API を足せば v1.1 で投稿解禁**できる。
  - **★評価**: **独自の評価フォーマット（自前レビュー由来の集計）を実装する方針に転換**（Google Places 連携は不採用）。外部 API 費用・規約制約が消える一方、評価の母数は自前レビューに依存する。クライアントは既に「rating が無ければ★非表示」実装済みなので、**v1 は評価なしで出荷し、v1.1 の投稿解禁とセットでバックエンド集計値を返し始めれば UI 側は無改修で表示される**。集計仕様（平均 or 中央値、少数母数の扱い、表示閾値）はバックエンド側で v1.1 までに設計する。
- バックエンド遅延は前提上考慮しないが、**単一障害点にはなる**（学生プロジェクトのホスティングは停止・費用切れが起きがち）。避難所は現行どおり SQLite シードで完全オフライン、観光もキャッシュを持つ構成にしておけば、サーバ停止時も「起動して使える」状態を維持できる。
- この判断を7月第2週までに確定させること。

#### A-3. モジュール境界の Lint 未導入

- `directory-structure.md` に「eslint-plugin-boundaries で自動検出する予定」とあるが未導入。人数が多い学生チームでは規約は必ず崩れるので、リリース前のリファクタが増える前に入れる。7月前半に導入すれば残り期間の逸脱を防げる。

#### A-4. 本番運用の観測性がゼロ

- クラッシュレポート・エラーモニタリングが無い。リリース後に「クラッシュしてます」の連絡だけが来る状態になる。
- **改善案**: `sentry-expo`（または Sentry React Native）を導入。ErrorBoundary を `app/_layout.tsx` の `AppProviders` に追加し、TanStack Query の `onError` と接続。EAS Update を併用すれば JS レベルの hotfix を審査なしで配布できる（後述）。

#### A-5. リリースパイプラインの不在

- eas.json は開発ビルドのみ。必要な追加:
  - `production` ビルドプロファイル（`autoIncrement: true`、channel: `production`）
  - `preview` プロファイル(TestFlight 内部テスト用)
  - `submit.production`（App Store Connect への自動提出）
  - **expo-updates 導入**（channel = production）: 審査後の軽微修正を OTA で当てられるのは、審査リードタイムが読めない9月リリースでは保険として大きい。
  - CI は lint/test のみ存在（`.github/workflows/`）。`typecheck` ジョブと、main へのマージで preview ビルドを走らせるワークフローを追加。

#### A-6. 設定画面の拡充（審査要件と一体）

- 現状は言語切替のみ。R-6 のとおり、プライバシーポリシー・クレジット（OSM/ORS/データ出典/OSS ライセンス）・問い合わせ・アプリバージョン表示を追加する。`expo-web-browser` が既にあるので外部リンクで済む。

#### A-7. 細かい技術負債（余裕があれば）

- `dev-client.apk`（ビルド済みバイナリ）・`.pnpm-store/`・`scripts/unlock-ios-signing.sh` がリポジトリ直下に untracked で存在 → `.gitignore` に追加（本計画のブランチで対応済み）。
- `@tanstack/react-query-devtools` を devDependencies へ。

## 3. チームベロシティの実績と見積もり

計画の前提として、チームの実測スループットを整理する（GitHub の実データ）。

### 3.1 実績（2026-06-16 リポジトリ作成 → 07-02 時点、約2.5週間）

| 指標               | 実績                                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| クローズ済み issue | 108 件（≒ 40〜45 タスク/週）                                                                                                                                                    |
| マージ済み PR      | 106 件（≒ 7 PR/日）                                                                                                                                                             |
| 成果物             | クライアント: 4層クリーンアーキテクチャ + 観光/避難/マナーの MVP UI + 3言語 i18n + SQLite オフライン + マップ経路。バックエンド: Onion Architecture の雛形 + tourism 縦切り実装 |

チーム全員が Claude Code を使いタスク分解 → 並列実行できる体制で、タスク粒度（30分〜半日）の issue 運用が回っている。これは一般的な学生チームの数倍のスループット。

### 3.2 残作業量の概算とボトルネックの所在

本ドキュメントのリリース必須項目（R-1〜R-9 + A-1〜A-6 + ストア準備）をチームのタスク粒度に分解すると **おおよそ 50〜70 タスク相当**。実績ペース（40 タスク/週）なら**純粋な開発量としては 1.5〜2 週間分**しかない。

ただし割引要素がある:

- これまでの実績は「モックデータ前提のグリーンフィールド UI 開発」で、Claude Code が最も速く回る領域。リリース工程は **実機検証・TestFlight の往復・権利処理・文言確認** など並列化できない待ち時間が多く、体感速度は 30〜50% 落ちるとみるべき。
- したがって開発系の残作業は **実質 3〜4 週間** と見積もる。

**結論: ボトルネックは開発速度ではなく外部リードタイム**（Apple Developer Program 加入、審査、画像・データの権利処理）。計画はこの外部待ちを最前倒しし、開発の余剰を「提出の前倒し」と「v1.1（レビュー投稿解禁）の先行開発」に振る。

## 4. リリーススケジュール（2026-07-02 → 9月中旬）

前提:

- 目標: **9/14–9/18 の週に App Store 正式公開**（前倒し可能なら 8月末公開 → 9月中旬に v1.1）
- スプリント番号は**チームの既存運用（1週間スプリント、Sprint 14 = 9/14 週）に合わせる**。Sprint 4（マナー MVP）・Sprint 5（統合 + 中間発表）は既に計画済みのため、リリース作業は Sprint 6 から本格化する
- バックエンドは雛形完成・2〜3日でデプロイ可能のため、**Sprint 6 前（7月中旬まで）に本番デプロイを完了**させる
- Apple の審査は通常 24–48h だが、**初回提出 + リジェクト1回**を織り込む。ベロシティに余裕があるため初回提出は **8/14** に前倒し（当初案の 8/28 から2週間短縮、バッファ4週間確保）
- スコープの大原則: **「v1 = 観光スポット閲覧 + マップ経路 + 避難所 + マナー + 3言語」。レビュー投稿・認証・独自★評価（自前レビュー集計）は v1.1**。バックエンドがあるため v1.1（モデレーション付き投稿 + 評価集計）は9月中に現実的

### 今すぐ着手（スプリントを待たない — リードタイムが長い順）
